# Git 협업 규칙

## 브랜치 운영

SETRON은 GitHub Pull Request(PR)로 변경 사항을 검토하고 병합합니다. `master`에는 릴리스한 코드를 유지하고, `develop`에는 다음 릴리스에 포함할 작업을 모읍니다. 두 브랜치는 계속 유지하며 직접 푸시하지 않습니다.

| 브랜치 | 분기 기준 | 용도와 병합 대상 |
| --- | --- | --- |
| `master` | 장기 브랜치 | 검증된 릴리스를 보관하고 버전 태그를 붙입니다. |
| `develop` | 장기 브랜치 | 기능과 수정을 통합하고 다음 릴리스를 준비합니다. |
| `feature/*` | `develop` | 새 기능을 개발한 뒤 `develop`에 병합합니다. 예시는 `feature/equipment-list`입니다. |
| `fix/*`, `docs/*`, `chore/*` | `develop` | 일반 오류 수정, 문서, 설정 변경을 각각 작업한 뒤 `develop`에 병합합니다. |
| `release/*` | `develop` | 출시할 범위를 확정하고 검증한 뒤 `master`에 병합합니다. 예시는 `release/ver1.0.0`입니다. |
| `hotfix/*` | `master` | 배포한 버전의 긴급 오류를 수정합니다. `master`에 먼저 병합하고 `develop`에도 반영합니다. |

작업 브랜치 이름은 영문 소문자와 하이픈으로 목적을 짧게 나타냅니다. 릴리스 브랜치는 `release/<버전 태그>` 형식으로 이름을 짓습니다.

## 작업 흐름

1. 최신 `origin/develop`에서 변경 목적에 맞는 작업 브랜치를 만듭니다.
2. 변경 범위에 맞춰 동작과 테스트를 확인합니다. 문서나 설정을 수정했다면 링크, 파일 경로, 설정 구문을 확인합니다.
3. 한 가지 목적을 기준으로 변경을 나눠 커밋하고 작업 브랜치를 GitHub에 푸시합니다.
4. `develop`을 대상으로 PR을 엽니다. 작업 중간에 리뷰를 요청할 때는 Draft로 표시합니다.
5. 리뷰 의견을 반영하고 충돌을 해결합니다. 코드가 바뀌면 영향을 받는 동작을 다시 검증합니다.
6. PR이 병합되고 변경 사항이 원격 `develop`에 반영되었는지 확인합니다. 로컬 `develop`을 갱신한 뒤 사용한 작업 브랜치를 정리합니다.

## 릴리스 흐름

`ver1.0.0`을 출시할 때는 다음 순서로 진행합니다.

1. 최신 `develop`에서 이번 버전에 포함할 변경을 확인하고 `release/ver1.0.0`을 만듭니다. 이후 릴리스 검증과 출시에 필요한 수정은 이 브랜치에서 진행합니다.
2. `release/ver1.0.0 → master` PR을 엽니다. 본문에 포함된 기능과 수정 사항, 검증 방법과 결과를 적습니다. 검증 뒤 릴리스 브랜치에 수정이 추가되면 해당 범위를 다시 확인합니다.
3. 리뷰와 검증을 마치면 GitHub에서 **Create a merge commit**으로 병합합니다. `master`에 생성된 이 병합 커밋에 `ver1.0.0` 태그를 붙입니다.
4. `master → develop` 동기화 PR을 열고 **Create a merge commit**으로 병합합니다. 두 브랜치에 릴리스 내역과 검증 과정의 수정이 모두 반영되었는지 확인한 뒤 릴리스 브랜치를 정리합니다.

## 긴급 수정

1. 배포한 버전에 긴급 오류가 발생하면 최신 `master`에서 `hotfix/*` 브랜치를 만듭니다.
2. 수정과 회귀 검증을 마친 뒤 `hotfix/* → master` PR을 엽니다. 리뷰 후 **Create a merge commit**으로 병합하고, 해당 병합 커밋에 새 패치 버전 태그를 붙입니다.
3. `master → develop` PR을 **Create a merge commit**으로 병합해 다음 버전에도 같은 수정이 포함되도록 합니다. 두 브랜치에 반영되었는지 확인한 뒤 긴급 수정 브랜치를 정리합니다.

## 커밋 메시지

Conventional Commits 형식을 사용합니다. type은 영문 소문자로 쓰고, 설명은 한국어로 간결하게 작성합니다.

```text
type: 변경 내용
type(scope): 변경 내용
```

`scope`는 선택 사항입니다. 필요한 경우 `ui`, `equipment`, `version`, `excel` 등 변경 영역을 적습니다.

| type | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | `feat(equipment): 설비 목록 조회 추가` |
| `fix` | 오류 수정 | `fix(excel): 빈 셀 검증 오류 수정` |
| `docs` | 문서 작성 및 수정 | `docs: 폴더 아키텍처 문서 추가` |
| `refactor` | 동작을 유지한 코드 구조 개선 | `refactor(version): 상대 버전 계산 로직 분리` |
| `test` | 테스트 추가 및 수정 | `test(version): 상대 버전 계산 테스트 추가` |
| `chore` | 설정 및 의존성 관리 | `chore: 프로젝트 초기 설정 추가` |
| `style` | 동작에 영향을 주지 않는 서식 변경 | `style: import 정렬 및 들여쓰기 정리` |

추가 설명이 필요하면 제목 아래 한 줄을 비우고 변경 이유와 영향을 본문에 적습니다. 호환성을 깨는 변경은 type 또는 scope 뒤에 `!`를 붙이거나 `BREAKING CHANGE:` 푸터로 표시합니다.

## PR 작성과 병합

PR은 하나의 목적을 가진 변경 단위로 작성합니다. 리뷰어가 이전 대화나 작업 과정을 몰라도 변경 이유와 결과를 이해할 수 있도록 설명합니다. 서로 독립적으로 검토하고 병합할 수 있는 작업은 별도의 PR로 분리합니다.

### 작성

일반 작업과 동기화 PR의 대상은 `develop`, 릴리스와 긴급 수정 PR의 대상은 `master`입니다. 제목은 커밋 메시지와 같은 형식을 사용하며, 작업 중 작성한 커밋을 나열하기보다 최종 변경 내용을 요약합니다.

```text
feat(equipment): 설비 목록 조회 기능 추가
```

본문에는 다음 내용을 작성합니다.

| 항목 | 작성 내용 |
| --- | --- |
| 변경 배경 | 해결하려는 문제와 변경이 필요한 이유 |
| 주요 변경 사항 | 추가·수정한 동작과 영향을 받는 기능 또는 모듈 |
| 검증 결과 | 확인한 동작, 테스트 방법과 결과. 확인하지 못한 항목이 있으면 사유도 기재 |
| 관련 자료 | 관련 이슈 링크. 화면이 바뀌면 변경 내용을 확인할 수 있는 스크린샷 첨부 |

### 리뷰

변경한 모듈을 이해하는 팀원에게 리뷰를 요청하고, 팀원 1명 이상의 리뷰를 받은 뒤 병합하는 방식을 권장합니다.

리뷰에서는 변경 목적에 맞게 동작하는지, 모듈 간 책임을 지키는지, 예외 상황과 필요한 검증을 다뤘는지 확인합니다. 리뷰 의견은 코드에 반영하거나 반영하지 않은 이유를 설명하고, 추가 논의가 필요한 내용은 병합 전에 합의합니다.

리뷰 이후 동작이나 영향 범위가 달라지면 PR 본문과 검증 결과도 갱신합니다.

### 병합

병합 전에는 리뷰 의견 처리 여부, 대상 브랜치와의 충돌 여부, 변경 범위에 필요한 검증 결과를 확인합니다. 자동 검사가 구성되어 있다면 검사 결과도 확인합니다. 충돌을 해결하면서 코드가 바뀐 경우에는 영향을 받는 동작을 다시 검증합니다.

일반 작업 브랜치를 `develop`에 병합할 때는 **Squash and merge**를 권장합니다. 최종 커밋 메시지는 PR의 변경 내용을 요약하고 커밋 규칙에 맞춰 작성합니다. 병합과 반영을 확인한 뒤 로컬과 원격 작업 브랜치를 정리합니다.

릴리스, 긴급 수정, `master → develop` 동기화 PR은 **Create a merge commit**으로 병합해 원래의 커밋 이력을 보존합니다.

## 규칙 변경

브랜치 전략, 커밋 형식, 리뷰 또는 병합 방식을 바꿀 때는 이 문서를 함께 수정하고 팀에 공유합니다.
